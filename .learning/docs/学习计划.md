# Authgear Server 系统和模型设计学习计划

本文档提供了系统学习 Authgear Server 项目架构和模型设计的完整路径。

## 第一阶段：理解核心概念（文档优先）

### 1. 从术语表开始
- **阅读文件**: `docs/specs/glossary.md`
- **目标**: 理解 User、Identity、Authenticator 等核心术语
- **重点概念**:
  - User（用户）
  - Identity（身份）
  - Authenticator（认证器）
  - Authentication Flow（认证流程）

### 2. 核心模型文档（按顺序阅读）

#### 2.1 用户模型
- **阅读文件**: `docs/specs/user-model.md`
- **核心内容**:
  - User（用户）结构
  - Identity（身份）类型：Login ID、OAuth、WebAuthn、Anonymous、Biometric
  - Authenticator（认证器）类型：Password、WebAuthn、TOTP、OOB-OTP
  - Account Status（账户状态）管理
- **关键理解点**:
  - 一个用户可以有多个身份
  - 一个用户可以有多个认证器
  - 身份用于识别用户，认证器用于验证用户

#### 2.2 认证与 OIDC 机制
- **阅读文件**: `docs/authn.md`
- **核心内容**:
  - Session（会话）系统：IdPSession、OfflineGrant、authn.Info
  - OAuth/OIDC 框架：Authorization、Grants
  - Session Resolution（会话解析）流程
  - Auth API 集成
- **关键理解点**:
  - 三种会话实现：IdPSession、OfflineGrant、authn.Info
  - OAuth 授权流程：Authorization → Grants
  - 会话在不同服务间的传递机制

#### 2.3 会话管理
- **阅读文件**: `docs/specs/sessions.md`
- **核心内容**:
  - 会话生命周期
  - 会话存储和验证
  - 会话过期机制

#### 2.4 认证流程设计
- **阅读文件**: `docs/specs/authentication-flow.md`
- **核心内容**:
  - Signup Flow（注册流程）
  - Login Flow（登录流程）
  - Reauth Flow（重新认证流程）
  - 流程步骤和分支设计
- **关键理解点**:
  - 声明式流程配置
  - 步骤类型和分支逻辑

### 3. 功能特性文档

#### 3.1 OIDC 实现
- **阅读文件**: `docs/specs/oidc.md`
- **了解**: OIDC 协议的具体实现细节

#### 3.2 WebAuthn/Passkey
- **阅读文件**: `docs/specs/webauthn.md`
- **了解**: 无密码认证的实现

#### 3.3 验证机制
- **阅读文件**: `docs/specs/verification.md`
- **了解**: 邮箱、手机号验证流程

#### 3.4 账户关联
- **阅读文件**: `docs/specs/account-linking.md`
- **了解**: 多个身份如何关联到同一用户

## 第二阶段：理解系统架构

### 1. 代码组织结构

```
pkg/lib/                    # 核心业务逻辑库
├── authn/                  # 认证核心
│   ├── user/              # 用户模型和服务
│   ├── identity/          # 身份模型和服务
│   └── authenticator/     # 认证器模型和服务
├── session/                # 会话管理
│   ├── idpsession/        # IdP 会话实现
│   ├── context.go         # 会话上下文
│   └── middleware.go      # 会话中间件
├── oauth/                  # OAuth/OIDC 实现
├── authenticationflow/    # 认证流程引擎
├── workflow/              # 工作流引擎
├── facade/                # 门面模式，统一接口
└── deps/                  # 依赖注入配置
```

### 2. 依赖注入架构

- **技术栈**: Google Wire
- **关键文件**:
  - `pkg/lib/deps/` - 根依赖配置
  - 各模块的 `deps.go` - 模块依赖定义
- **理解要点**:
  - 每个功能模块都有独立的依赖集合
  - 通过 `DependencySet` 组织依赖关系
  - 使用接口定义服务，支持测试和扩展

### 3. 数据模型映射

理解三层模型结构：

1. **文档模型** (`docs/specs/`)
   - 概念定义和规范说明

2. **API 模型** (`pkg/api/model/`)
   - REST API 和 GraphQL API 使用的模型
   - 文件示例：
     - `pkg/api/model/user.go`
     - `pkg/api/model/identity.go`
     - `pkg/api/model/authenticator.go`

3. **业务层模型** (`pkg/lib/authn/`)
   - 内部业务逻辑使用的模型
   - 文件示例：
     - `pkg/lib/authn/user/model.go`
     - `pkg/lib/authn/identity/`
     - `pkg/lib/authn/authenticator/`

## 关键设计模式

### 1. 依赖注入（Dependency Injection）
- **技术**: Google Wire
- **位置**: 各模块的 `deps.go` 文件
- **优势**: 解耦、可测试、易扩展

### 2. 门面模式（Facade Pattern）
- **位置**: `pkg/lib/facade/`
- **作用**: 为复杂的子系统提供统一接口
- **示例**: `UserFacade`、`IdentityFacade`

### 3. 服务层模式（Service Layer Pattern）
- **特点**: 每个功能模块都有独立的 Service
- **示例**: `UserService`、`IdentityService`、`AuthenticatorService`

### 4. 存储抽象（Storage Abstraction）
- **特点**: 使用接口定义存储层
- **优势**: 支持多种实现（Redis、数据库等）
- **示例**: `Store` 接口及其实现
