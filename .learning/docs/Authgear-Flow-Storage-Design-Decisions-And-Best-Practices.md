## 一、核心设计决策解析

### 1.1 为什么使用双键模式？

#### 问题背景

在认证流程中，我们需要：
1. 快速验证一个流程是否有效（存在性检查）
2. 存储和读取完整的流程状态数据
3. 支持流程的"软删除"（使状态失效但保留历史）

#### 单键方案的问题

```
方案 A: 单键存储 (不推荐)
┌────────────────────────────────────────┐
│ Key: app:{id}:flow:{flowID}            │
│ Value: JSON(Flow)                      │
│                                        │
│ 问题:                                   │
│ 1. 每次状态更新都要覆盖整个 Value         │
│ 2. 无法保留历史状态                      │
│ 3. 删除时需要清理所有历史状态             │
└────────────────────────────────────────┘
```

#### Authgear 的双键方案

```
方案 B: 双键存储 (Authgear 采用)
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│ Flow Key              State Key (历史版本)                   │
│ ┌─────────────────┐   ┌─────────────────┐                     │
│ │ flow:{flowID}   │   │ state:{token1}  │ ← 初始状态           │
│ │ Value: "exist"  │   │ Value: JSON(v1) │                     │
│ │                 │   └─────────────────┘                     │
│ │ 作用: 验证存在性  │   ┌─────────────────┐                     │
│ │ 删除: 软删除     │   │ state:{token2}  │ ← 第一次输入后        │
│ └─────────────────┘   │ Value: JSON(v2) │                     │
│                       └─────────────────┘                     │
│                       ┌─────────────────┐                     │
│                       │ state:{token3}  │ ← 第二次输入后        │
│                       │ Value: JSON(v3) │                     │
│                       └─────────────────┘                     │
│                                                             │
│ 验证流程: 1. 读 state:{token} → 获取 FlowID                  │
│          2. 验证 flow:{FlowID} 存在                          │
│          3. 两者都存在 → 流程有效                            │
│                                                             │
│ 删除流程: 仅删除 flow:{flowID}                               │
│          所有 state keys 通过 TTL 自动过期                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

#### 双键模式的优势

| 优势 | 说明 |
|------|------|
| **软删除** | 删除 flowKey 即可使所有历史状态失效，无需清理 |
| **历史追溯** | 在 TTL 期内可以查看流程的历史状态 |
| **并发安全** | 新状态创建新的 key，无并发修改问题 |
| **验证效率** | 存在性检查只需要读取很小的 flowKey |

### 1.2 为什么每次更新都生成新的 StateToken？

#### 不可变状态设计的优势

```
可变状态设计 (不推荐):
┌─────────────────────────────────────────┐
│ 客户端                  服务器            │
│   │                       │             │
│   │──── 请求 A ──────────>│             │
│   │                       │ 修改状态     │
│   │                       ▼             │
│   │                    ┌─────┐         │
│   │                    │状态A │         │
│   │<─── StateTokenA ────┤     │         │
│   │                    └──┬──┘         │
│   │ 请求 B (TokenA)       │             │
│   │─────────────────────>│             │
│   │                       │ 修改状态     │
│   │                       ▼             │
│   │                    ┌─────┐         │
│   │                    │状态B │ ◄── 状态A被覆盖 │
│   │<─── StateTokenA ────┤     │         │
│   │                    └─────┘         │
│                                         │
│ 问题:                                     │
│ - 并发请求可能互相覆盖                     │
│ - 无法回滚到之前的状态                     │
│ - 客户端可能持有过期令牌                     │
└─────────────────────────────────────────┘

不可变状态设计 (Authgear 采用):
┌─────────────────────────────────────────┐
│ 客户端                  服务器            │
│   │                       │             │
│   │──── 请求 A ──────────>│             │
│   │                       │ 创建新状态   │
│   │                       ▼             │
│   │                    ┌───────┐         │
│   │                    │状态A  │         │
│   │<── StateTokenA ────┤       │         │
│   │                    └───┬───┘         │
│   │                        │             │
│   │ 请求 B (TokenA)        │             │
│   │───────────────────────>│             │
│   │                       │ 创建新状态   │
│   │                       ▼             │
│   │                    ┌───────┐         │
│   │                    │状态B  │         │
│   │                    │(基于A)│         │
│   │<── StateTokenB ────┤       │         │
│   │                    └───┬───┘         │
│   │                        │             │
│   │ 请求 C (TokenA-过期)   │             │
│   │───────────────────────>│             │
│   │                       X 拒绝         │
│   │                          (TokenA已失效)│
│                                         │
│ 优势:                                     │
│ - 每个令牌对应确定的状态                   │
│ - 无并发修改问题                          │
│ - 可以检测客户端持有过期令牌                 │
│ - 支持幂等性（相同令牌重复请求无影响）          │
└─────────────────────────────────────────┘
```

#### StateToken 变更流程

```
┌─────────────────────────────────────────────────────────────┐
│                    StateToken 生命周期                       │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  创建流程                                                    │
│     │                                                       │
│     ▼                                                       │
│  ┌─────────────┐    第一次输入                                │
│  │ Token: A    │───────────────────┐                          │
│  │ State: 初始  │                   │                          │
│  └─────────────┘                   ▼                          │
│                              ┌─────────────┐                 │
│                              │ Token: B    │                  │
│                              │ State: 状态1 │                 │
│                              └─────────────┘                 │
│                                    │                        │
│                                    │ 第二次输入               │
│                                    ▼                        │
│                              ┌─────────────┐                 │
│                              │ Token: C    │                  │
│                              │ State: 状态2 │                  │
│                              └─────────────┘                 │
│                                    │                        │
│                                    │ 流程完成                 │
│                                    ▼                        │
│                              ┌─────────────┐                 │
│                              │ 删除流程      │                 │
│                              │ (仅删 flowKey)│                 │
│                              └─────────────┘                 │
│                                                             │
│  结果: A, B, C 三个 stateKey 都还存在，但通过 TTL 过期        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 1.3 为什么分离 Session 和 Flow State？

#### 数据分类原则

```
┌──────────────────────────────────────────────────────────────┐
│                     数据分类对比                               │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  Session (配置数据)              Flow State (执行数据)          │
│  ┌─────────────────────┐        ┌─────────────────────┐       │
│  │ • OAuthSessionID    │        │ • Intent            │       │
│  │ • SAMLSessionID     │        │ • StateToken        │       │
│  │ • ClientID          │        │ • Nodes (执行路径)    │       │
│  │ • RedirectURI       │        │                     │       │
│  │ • Prompt            │        │ 特点:               │       │
│  │ • State/XState      │        │ • 频繁变更           │       │
│  │ • UILocales         │        │ • 每次输入都更新      │       │
│  │ • BotProtection...  │        │ • 需要保留历史        │       │
│  │ • LoginHint         │        │                     │       │
│  └─────────────────────┘        └─────────────────────┘       │
│                                                              │
│  特点:                          为什么分离？                    │
│  • 创建后基本不变                • 减少 Session 写操作          │
│  • 与 OAuth/SAML 协议相关      • 独立 TTL 管理               │
│  • 跨流程可能复用                • 不同的访问模式              │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

#### 存储操作对比

| 操作 | Session | Flow State | 说明 |
|------|---------|------------|------|
| 创建 | 1 次 | N 次 | Session 只在流程开始时创建 |
| 读取 | 每次请求 | 每次请求 | 两者都需要 |
| 更新 | 偶尔 | 频繁 | Flow State 每次输入都更新 |
| 删除 | 流程结束 | 自动过期 | Session 显式删除，State 依赖 TTL |

### 1.4 为什么只删除 flowKey 而不清理所有 stateKey？

#### 删除策略对比

```
方案 A: 清理所有状态键 (不推荐)
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│ 删除流程:                                                    │
│   1. 查询所有 stateKey (需要扫描或维护索引)                   │
│   2. 批量删除                                                 │
│   3. 删除 flowKey                                            │
│                                                             │
│ 问题:                                                        │
│ • 需要维护 stateToken → flowID 的反向索引                    │
│ • 批量删除操作原子性难以保证                                 │
│ • 删除失败时需要重试/清理逻辑                                │
│ • 增加代码复杂度                                             │
│                                                             │
└─────────────────────────────────────────────────────────────┘

方案 B: 仅删除 flowKey (Authgear 采用)
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│ 删除流程:                                                    │
│   1. 删除 flowKey                                            │
│   2. 完成！                                                   │
│                                                             │
│ 验证流程有效性:                                               │
│   1. 读取 stateKey → 获取 FlowID                             │
│   2. 检查 flowKey 是否存在                                    │
│   3. 不存在 → 返回 ErrFlowNotFound                           │
│                                                             │
│ 历史状态键处理:                                               │
│   • 通过 TTL 自动过期                                        │
│   • 无需额外操作                                              │
│   • 在过期前占用少量内存                                      │
│                                                             │
│ 优势:                                                        │
│ • 删除操作 O(1) 复杂度                                       │
│ • 无需要维护额外索引                                          │
│ • 原子性保证简单                                              │
│ • 代码简洁可维护                                              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

#### 内存占用估算

```
假设条件:
- 平均每个流程产生 5 个历史状态
- 每个状态数据大小: 10KB
- 用户交互时间: 20分钟 (TTL)
- QPS: 1000 流程/秒

内存占用计算:
- 每秒产生 5000 个 stateKey (1000 × 5)
- 20分钟内产生: 5000 × 1200 = 6,000,000 个 stateKey
- 峰值内存: 6M × 10KB = 60GB

优化建议 (如果内存敏感):
1. 缩短 TTL (如 5 分钟)
2. 压缩序列化数据
3. 使用 Redis 内存淘汰策略
```

## 二、关键权衡决策

### 2.1 一致性 vs 可用性

```
┌──────────────────────────────────────────────────────────────┐
│                   CAP 权衡选择                                │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  Authgear 的选择: 优先可用性 (AP)                            │
│                                                              │
│  理由:                                                        │
│  1. 认证流程是用户体验的关键路径                               │
│  2. 短暂的旧状态读取不会导致安全问题                            │
│  3. Redis 的主从复制提供最终一致性                               │
│                                                              │
│  潜在问题:                                                   │
│  • 主从切换时可能读取旧状态                                     │
│  • 极端情况下状态不一致                                        │
│                                                              │
│  缓解措施:                                                   │
│  • 使用 Redis Sentinel/Cluster 提高可用性                      │
│  • 业务逻辑设计为幂等                                         │
│  • 状态令牌具有时效性                                          │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 2.2 内存 vs 查询复杂度

```
决策: 使用 JSON 序列化整个 Flow 对象

┌─────────────────────────────────────────────────────────────┐
│                                                             │
│ 方案对比:                                                    │
│                                                             │
│ 方案 A: Hash 结构                                            │
│   HSET flow:{id} flow_id xxx state_token yyy ...            │
│   • 优势: 可以单独读取/更新字段                              │
│   • 劣势: 复杂结构难以存储 (Nodes 数组)                      │
│                                                             │
│ 方案 B: JSON 字符串 (Authgear 采用)                          │
│   SET state:{token} {JSON(Flow)}                            │
│   • 优势: 支持任意复杂结构，代码简洁                          │
│   • 劣势: 读取整个对象，不能部分更新                         │
│                                                             │
│ 决策理由:                                                    │
│ • Flow 结构复杂（支持嵌套子流程）                             │
│ • 每次更新都是全量替换（生成新 StateToken）                    │
│ • JSON 序列化在现代语言中支持良好                             │
│ • 可读性好，便于调试                                          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 三、最佳实践指南

### 3.1 复刻此设计的检查清单

```markdown
□ 1. 键命名规范
   □ 使用 app:{appID} 前缀实现多租户隔离
   □ 使用明确的命名空间 (authenticationflow_xxx)
   □ 区分数据类型 (flow/state/session/events)

□ 2. 双键模式实现
   □ flowKey 仅作为存在性标记
   □ stateKey 存储完整序列化数据
   □ Get 操作必须双键验证
   □ Delete 只删除 flowKey

□ 3. 不可变状态
   □ 每次更新生成新 StateToken
   □ 不修改已存在的 stateKey
   □ 依赖 TTL 清理历史状态

□ 4. 数据分离
   □ Session 和 Flow State 分开存储
   □ 识别配置数据和执行数据
   □ 根据变更频率选择存储策略

□ 5. 错误处理
   □ 明确定义 ErrFlowNotFound
   □ 正确处理 Redis Nil 错误
   □ 区分业务错误和系统错误

□ 6. TTL 管理
   □ 所有键都有 TTL
   □ TTL 时长符合业务需求
   □ 考虑安全性和用户体验平衡

□ 7. 序列化
   □ 选择适合复杂结构的序列化方案
   □ 确保所有嵌套类型可序列化
   □ 考虑序列化性能
```

### 3.2 常见反模式

```
❌ 反模式 1: 直接修改 Redis 中的状态

错误代码:
    flow := store.GetFlow(stateToken)
    flow.Nodes = append(flow.Nodes, newNode)
    redis.Set(stateKey, flow)  // 复用旧 stateToken

问题:
    - 并发请求可能互相覆盖
    - 客户端缓存的 StateToken 对应不确定状态
    - 无法检测客户端持有过期令牌

正确做法:
    flow := store.GetFlow(stateToken)
    newFlow := &Flow{
        FlowID:     flow.FlowID,      // 保持相同
        StateToken: newStateToken(),  // 生成新的
        Intent:     flow.Intent,
        Nodes:      append(flow.Nodes, newNode),
    }
    store.CreateFlow(newFlow)  // 创建新状态
```

```
❌ 反模式 2: 忽略双键验证

错误代码:
    data := redis.Get(stateKey)
    flow := unmarshal(data)
    return flow  // 没有验证 flowKey

问题:
    - 流程删除后，旧 stateToken 仍能读取状态
    - 安全风险：访问已终止的流程

正确做法:
    data := redis.Get(stateKey)
    if data == nil {
        return ErrFlowNotFound
    }
    flow := unmarshal(data)
    if !redis.Exists(flowKey(flow.FlowID)) {
        return ErrFlowNotFound  // 流程已删除
    }
    return flow
```

```
❌ 反模式 3: 删除时清理所有 stateKey

错误代码:
    for _, token := range allStateTokens {
        redis.Del(stateKey(token))  // 大量删除操作
    }
    redis.Del(flowKey)

问题:
    - 需要维护 stateToken 列表
    - 删除操作量大
    - 原子性难以保证

正确做法:
    redis.Del(flowKey)  // 仅删除存在性标记
    // 历史 stateKey 依赖 TTL 过期
```

```
❌ 反模式 4: Session 和 Flow 状态耦合

错误代码:
    type Flow struct {
        FlowID     string
        StateToken string
        Intent     Intent
        Nodes      []Node
        ClientID   string   // OAuth 参数混入
        RedirectURI string  // OAuth 参数混入
    }

问题:
    - Session 数据随每次 Flow 更新重复写入
    - 违反单一职责原则
    - 增加存储开销

正确做法:
    type Session struct {
        FlowID      string
        ClientID    string   // OAuth 参数
        RedirectURI string
    }

    type Flow struct {
        FlowID     string
        StateToken string
        Intent     Intent
        Nodes      []Node
    }
```

### 3.3 性能优化建议

```
┌──────────────────────────────────────────────────────────────┐
│                   性能优化策略                                │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│ 1. Pipeline 批量操作                                          │
│    ┌─────────────────────────────────────────────────────┐   │
│    │ pipe := client.Pipeline()                           │   │
│    │ pipe.SetEX(ctx, flowKey, value, ttl)                │   │
│    │ pipe.SetEX(ctx, stateKey, data, ttl)                │   │
│    │ _, err := pipe.Exec(ctx)                            │   │
│    └─────────────────────────────────────────────────────┘   │
│                                                              │
│ 2. 数据压缩                                                   │
│    ┌─────────────────────────────────────────────────────┐   │
│    │ compressed := gzipCompress(jsonData)                │   │
│    │ redis.Set(stateKey, compressed, ttl)                │   │
│    │ // 可减少 50-80% 内存占用                            │   │
│    └─────────────────────────────────────────────────────┘   │
│                                                              │
│ 3. 连接池优化                                                 │
│    ┌─────────────────────────────────────────────────────┐   │
│    │ &redis.Options{                                     │   │
│    │     PoolSize:     100,  // 根据并发调整              │   │
│    │     MinIdleConns: 10,   // 保持最小连接              │   │
│    │     MaxRetries:   3,    // 自动重试                  │   │
│    │ }                                                   │   │
│    └─────────────────────────────────────────────────────┘   │
│                                                              │
```

## 五、总结

Authgear Flow Redis 存储设计的核心亮点:

1. **双键模式**: 巧妙解决存在性验证和历史状态清理问题
2. **不可变状态**: 通过生成新 StateToken 实现并发安全
3. **数据分离**: Session 和 Flow State 分离存储，减少冗余
4. **TTL 设计**: 利用 Redis 原生 TTL 机制自动清理过期数据
5. **JSON 序列化**: 支持复杂嵌套结构，代码简洁

复刻此设计时，最关键的是理解**双键模式**和**不可变状态**这两个核心概念。它们解决了分布式状态管理中的常见难题：并发修改、状态失效和历史清理。
